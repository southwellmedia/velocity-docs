You need Node 22.23.4 or newer.

<Aside title="Beta">
The packages are on npm as `@velocity-astro/cms-*`. Versions are `0.x`, so pin the one you install.
`npm view @velocity-astro/cms-astro version` says which is the latest, and the
[changelog](https://github.com/Velocity-Astro/velocity-cms/blob/main/CHANGELOG.md) says what each one changed.
</Aside>

## Try the starter

The repository has a small site that is plain Astro: pages built from sections, a blog, a contact form and a menu.
It is the fastest way to see the CMS, and the best thing to copy from. It needs pnpm 10.

```sh
git clone https://github.com/Velocity-Astro/velocity-cms.git
cd velocity-cms
pnpm install
pnpm build

cd examples/starter
npx velocity-cms init you@example.com "Your Name"
npm run seed
npm run dev
```

`init` prints a link that signs you in. Open it once the site is running, then open **Pages** and change something.

## Add it to a site

In an Astro site that has a server adapter:

<Steps>

1. Set the site up.

   ```sh
   npx velocity-cms init you@example.com "Your Name"
   ```

   This writes a secret and the local address to `.env`, keeps `.env` and the database's folder out of git, adds
   `velocityCms()` to the Astro config and makes you the site's owner. It can be run again: it adds only what is
   missing and never changes a value that is there.

   If you would rather use Astro's own command, `npx astro add @velocity-astro/cms-astro` installs the package and
   adds the integration to the Astro config. Run `init` afterwards for the secret, the owner and the agent files:
   it adds only what is missing.

2. Describe your content. See [Content types and fields](/cms/content-types/).

3. Draw it. See [Showing content](/cms/showing-content/) and [Sections](/cms/page-builder/).

</Steps>

`init` prints a link that signs you in. Start the site (`npm run dev` or `pnpm dev`), then open the link. It works
once, for ten minutes; `npx velocity-cms link you@example.com` prints a new one.

The editor you land in is empty: no content types, no pages. That is expected. The CMS never guesses what your
site holds, so steps 2 and 3 are where it meets your pages. The quickest way to see both done is the
[starter](#try-the-starter): its `cms/model.mjs`, its one route and its section components are small enough to
read in a sitting and copy from. To move an existing site over, follow [Converting a template](/cms/converting-a-template/)
step by step.

Without an email and a name, `init` stops after the setup. Make the owner later with
`npx velocity-cms owner <email> <name>`. `npx velocity-cms link <email>` prints a new sign-in link for someone who
already has access.

### On a Velocity site

The free Velocity starter (`npm create velocity-astro`) does not include the CMS. It is a static site whose
content lives in files, and it stays one until you add the CMS with the command above. The starter already has a
server adapter, so `init` needs nothing else, and the site builds and runs as before.

After `init`, the starter's own pages are still drawn from its files. A page becomes editable when you describe
its content and read it from the CMS, as steps 2 and 3 say. Pages you do not move stay static.

[Velocity Premium](/premium/) templates are the other way to start: a template on the CMS has its content types,
sections and sample content already made.

### What the config looks like

```js
// astro.config.mjs
import { defineConfig, memoryCache } from 'astro/config';
import node from '@astrojs/node';
import velocityCms from '@velocity-astro/cms-astro';

export default defineConfig({
  site: process.env.SITE_URL || 'http://localhost:4321',
  adapter: node({ mode: 'standalone' }),
  integrations: [velocityCms({ siteName: 'My site', entryPages: ['pages'] })],
  // A page drawn from the CMS is kept until a publish clears it. A day is the backstop.
  cache: { provider: memoryCache() },
  routeRules: { '/[...path]': { maxAge: 86400, tags: ['cms'] } },
});
```

| Option | What it is for |
|---|---|
| `siteName` | Shown in the editor, in sign-in emails and in the passkey prompt. |
| `entryPages` | The content types whose entries are pages one route draws, such as `['pages']`. Their addresses join the sitemap and search. |
| `plugins` | The site's own plugins: package names or files. See [Writing a plugin](/cms/plugins/). |
| `mailer` | A file that delivers sign-in links by email. See [People and sign-in](/cms/people/). |
| `images` | A folder of images that image fields can choose from, such as `'./src/assets/photos'`. |
| `unlisted` | Addresses to leave out of the sitemap, such as `['/search/']`. |

## Settings

The CMS reads its settings from the environment, and from `.env` while you develop and build.

| Variable | |
|---|---|
| `VELOCITY_CMS_SECRET` | Required. At least 32 characters. Signs sessions and preview links and seals plugin secrets. `init` makes one. |
| `VELOCITY_CMS_ORIGIN` | The site's address, such as `https://example.com`. Not needed when `site` is set in the Astro config. |
| `VELOCITY_CMS_DATABASE_URL` | Where the database is. Left out, a file at `cms/data.db`. |
| `VELOCITY_CMS_DATABASE_TOKEN` | The token of a hosted libSQL database. |
| `VELOCITY_CMS_RESEND_API_KEY`, `VELOCITY_CMS_EMAIL_FROM` | Send sign-in links and invitations through Resend. |
| `VELOCITY_CMS_MEDIA_DIR` | A folder for uploaded images. |
| `VELOCITY_CMS_S3_BUCKET`, `VELOCITY_CMS_S3_ENDPOINT`, `VELOCITY_CMS_S3_ACCESS_KEY_ID`, `VELOCITY_CMS_S3_SECRET_ACCESS_KEY` | A bucket for uploaded images. All four, or none. `VELOCITY_CMS_S3_REGION` is optional. |

### Set up in the editor

An owner sets these under **Settings** in the editor, with no change to the server and no redeploy:

| Tab | What it sets |
|---|---|
| **General** | What the site is called in the editor and in its emails. |
| **Email** | The email service (Resend), its API key and who email comes from, with a test email to yourself. |
| **Storage** | The S3-compatible bucket uploads are kept in, with a test that writes a file and reads it back. |
| **Forms and spam** | The spam check (Cloudflare Turnstile or Google reCAPTCHA v3) and its two keys, and how many messages one address may send. |

Keys are sealed with `VELOCITY_CMS_SECRET` and never sent back to the browser. Where the server's environment
already sets one of these (`VELOCITY_CMS_RESEND_API_KEY`, `VELOCITY_CMS_S3_*`), the environment wins and the tab
says so. The secret, the database and the site's address are always settings of the server.

<Aside type="caution">
Sign-in links are made for the configured address, never for the address a request claims to come from. A deployed
site with neither `site` nor `VELOCITY_CMS_ORIGIN` cannot send a working link.
</Aside>

## Deploy on a server

Any machine that runs Node and keeps its disk.

<Steps>

1. Set `VELOCITY_CMS_SECRET` and the site's address on the machine.
2. Build and start the site as you would any Astro site on the Node adapter.
3. Make the owner once, on the machine: `npx velocity-cms owner you@example.com "Your Name"`.

</Steps>

The database is the file `cms/data.db` and uploads go in `cms/media`, beside it. Back that folder up.

## Deploy on Vercel

A serverless host has no disk to keep, so the database and the uploads live elsewhere.

<Steps>

1. Create a libSQL database, for example on [Turso](https://turso.tech), and set `VELOCITY_CMS_DATABASE_URL` and
   `VELOCITY_CMS_DATABASE_TOKEN` in the project's settings.
2. Set `VELOCITY_CMS_SECRET`, and `site` in the Astro config (or `VELOCITY_CMS_ORIGIN`).
3. Use the Vercel adapter in place of the Node one, and deploy.
4. Make the owner from your own machine, with the same four variables in your shell or `.env`:
   `npx velocity-cms owner you@example.com "Your Name"`.

</Steps>

For uploads, name an S3-compatible bucket, such as Cloudflare R2: in the editor under **Settings**, **Storage**,
or with the four `VELOCITY_CMS_S3_*` variables. Until one is named, a site on a hosted database takes no uploads,
and the editor does not offer any.

For email, add a Resend key under **Settings**, **Email**, or set `VELOCITY_CMS_RESEND_API_KEY` and
`VELOCITY_CMS_EMAIL_FROM`. Until then, nobody you invite can be emailed a sign-in link: print one with
`npx velocity-cms link <email>` from your own machine.

## Deploy on Cloudflare Workers

<Aside type="caution" title="Experimental">
On Workers the CMS has run on a deployed site with D1, R2 and Cloudflare's Images binding: pages, the editor,
publishing, scheduled publishing, uploads and forms. Email, passkeys and plugins that send out have not been tried
there yet. Try it on a site you can afford to set up twice.
</Aside>

With the Cloudflare adapter the CMS is a Worker. The content lives in a D1 database and uploads in an R2 bucket,
both reached by binding, so there is no address and no key to keep.

<Steps>

1. Use the Cloudflare adapter: `npx astro add cloudflare`.
2. Make the database and the bucket, and bind them in the Wrangler config:

   ```sh
   npx wrangler d1 create my-site
   npx wrangler r2 bucket create my-site-media
   ```

   ```jsonc
   // wrangler.jsonc
   {
     "compatibility_date": "2026-11-01",
     "compatibility_flags": ["nodejs_compat"],
     "d1_databases": [{ "binding": "DB", "database_name": "my-site", "database_id": "<the id d1 create printed>" }],
     "r2_buckets": [{ "binding": "MEDIA", "bucket_name": "my-site-media" }]
   }
   ```

3. Run `npx velocity-cms init`. It reads the two bindings and writes them to `.env`, which a Worker reads while
   you develop:

   ```sh
   VELOCITY_CMS_DATABASE_URL=d1:DB
   VELOCITY_CMS_R2_BUCKET=MEDIA
   ```

4. Keep pages in Cloudflare's cache, which every copy of the Worker shares and a publish clears:

   ```js
   // astro.config.mjs
   import { cacheCloudflare } from '@astrojs/cloudflare/cache';

   export default defineConfig({
     cache: { provider: cacheCloudflare() },
     routeRules: { '/[...path]': { maxAge: 86400, tags: ['cms'] } },
   });
   ```

5. For the deployed Worker, set the secret with `npx wrangler secret put VELOCITY_CMS_SECRET`, and put
   `VELOCITY_CMS_ORIGIN`, `VELOCITY_CMS_DATABASE_URL` and `VELOCITY_CMS_R2_BUCKET` under `vars` in the Wrangler
   config. Then deploy.

</Steps>

The commands work as they do elsewhere. `owner`, `link`, `token` and a seed script reach the D1 database through
Wrangler, which the site installs. That is the local database `astro dev` and `wrangler dev` use. To reach the
real one, mark the binding `"remote": true` in the Wrangler config, in an environment of its own if you like
(`CLOUDFLARE_ENV` names it).

Three things differ from a server:

- **A save is kept whole or not at all.** D1 holds no transaction open, so each save is sent as one batch. When
  what it was decided from changed meanwhile, it is refused as a conflict, which the editor already handles.
- **Images are made lighter by Cloudflare's Images binding** (`IMAGES`, which the adapter adds), since the library
  used elsewhere does not run in a Worker.
- **A page built ahead of time with a library a Worker cannot load**, such as `sharp`, needs
  `cloudflare({ prerenderEnvironment: 'node' })`, so that it is built in Node.

<Aside>
Node on a server and Vercel are the hosts the CMS has been run on. Cloudflare Workers is experimental. Netlify is
untried.
</Aside>

## A timer, if you want one

Scheduled publishing needs no timer: the site looks for what is due whenever a page is asked for. On a quiet site
that can be late. A scheduled job (cron, or your host's own) that calls one address makes it exact:

```sh
curl -H "Authorization: Bearer $VELOCITY_CMS_SECRET" https://example.com/api/cms/schedule
```
