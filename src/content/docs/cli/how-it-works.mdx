The CLI contains no template files. Everything a project can contain lives in the [Velocity repository](https://github.com/southwellmedia/velocity), and `velocity-manifest.json` declares how the pieces combine. The CLI applies that recipe.

```
Resolve the source (latest release, --ref or --template)
    │
    ▼
Download Velocity to a temporary folder
    │
    ▼
Check the manifest's version requirements
    │
    ▼
Apply variants → select components → clean up
    │
    ▼
Copy into your project folder
    │
    ▼
Generate pages, write package.json and .velocity.json
    │
    ▼
Initialize git and install dependencies
```

<Aside type="tip" title="Why it works this way">
  In CLI 1.x, the CLI carried its own copies of Velocity files, and they drifted out of date. Now Velocity's CI scaffolds and builds all eight project shapes, so a change that breaks one fails in Velocity's pull request.
</Aside>

## Choosing a Velocity Version

| Source | How | Notes |
|--------|-----|-------|
| Latest release | Default | Falls back to the `main` branch, with a notice, if GitHub can't be reached |
| Tag or branch | `--ref v2.0.0` | Works for `upgrade` too |
| Local checkout | `--template ../velocity` | Skips `node_modules`, `dist`, `.git` and other build folders |

Set `GITHUB_TOKEN` or `GH_TOKEN` if you hit GitHub's API rate limit when the CLI looks up the latest release.

## Version Requirements

The manifest's `scaffold` section sets what's required:

| Field | Effect |
|-------|--------|
| `minCliVersion` | The CLI stops and asks you to update if it's too old |
| `node` | The CLI warns when scaffolding and stops when upgrading if your Node version doesn't match |

A Velocity version with no `scaffold` section, such as 1.x, is refused.

## Variants

Variants are applied in order. Each one runs only when its `when` condition matches your options:

| Variant | When | What it does |
|---------|------|--------------|
| `i18n` | `--i18n` | Enables `es` and `fr` and adds their site copy |
| `demo` | `--demo` | Keeps every component, because the demo pages use them all |
| `minimal` | No `--demo` | Replaces the home view and nav config, and removes demo pages, landing components and sample content |

A variant can overlay whole files from `variants/<name>/`, remove paths, and add components that must be kept:

```json
{
  "id": "minimal",
  "when": { "demo": false },
  "overlay": "variants/minimal",
  "remove": ["src/components/landing", "src/pages/about.astro"]
}
```

The full contract is in [`variants/README.md`](https://github.com/southwellmedia/velocity/blob/main/variants/README.md).

## Scaffolding Steps

<Steps>
1. **Fetch the template** into a temporary folder.

2. **Check version requirements.**

3. **Run the variant pipeline:** apply variants, prune components, then delete repo-only files such as `variants/` and the scaffold test scripts.

4. **Remove `.git` and other package managers' lockfiles.** With pnpm, the CI-tested `pnpm-lock.yaml` is kept.

5. **Copy the result** into your project folder.

6. **Generate starter pages** if you asked for any.

7. **Update `package.json`** with your project name.

8. **Write `.velocity.json`.** It records the Velocity version, your options and file hashes, which [`upgrade`](/cli/upgrade/) uses later.

9. **Seed the site brief** for an own site: `.agents/site.md` with your site name, description, languages and starter pages, plus the site name in `site.config.ts` and the README.

10. **Install dependencies,** unless you passed `--no-install`.

11. **Initialize git,** so the first commit holds the finished project.
</Steps>

## Component Registry

`component-registry.json` in Velocity describes each component:

```json
{
  "components": {
    "contact-form": {
      "name": "ContactForm",
      "category": "patterns",
      "files": ["src/components/patterns/ContactForm.astro"],
      "dependencies": { "utilities": ["cn"], "components": ["input", "textarea", "button"] }
    }
  }
}
```

| Field | Description |
|-------|-------------|
| `name` | Display name |
| `category` | Category grouping |
| `subcategory` | Subcategory within UI |
| `files` | Component file paths |
| `dependencies` | Required utilities and components |

To prune components, the CLI resolves your selection and its dependencies, adds the always-included components, and deletes the rest of the optional folders.

## Package Managers

The wizard preselects the package manager you ran it with and lets you change it. With `--yes`, the CLI uses the package manager you ran it with. If installation fails, the project is still created and the CLI tells you which command to run.
